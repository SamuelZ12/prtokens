# prtokens — per-PR token cost attribution (v0 design)

**Date:** 2026-06-12
**Status:** Approved design, pre-implementation
**Working name:** `prtokens` (final name pending npm/GitHub availability check)

## 1. Problem & motivation

Coding agents now produce a large share of merged code, and agentic pricing is
shifting to usage-based billing (June 2026 Copilot pricing backlash: power-user
bills up 10–50x; documented cases of $8,400 first-month bills from per-PR
agents). A single agentic task pushes 400K–2M input tokens. Engineering teams
account for work in PRs — review, DORA metrics, changelogs all hang off the
PR — but no tool answers "what did this PR cost in tokens?"

Existing tools measure the wrong dimension for that question:

- **ccusage** (de facto standard, multi-agent): aggregates by day/session/project; no GitHub join.
- **LLM observability** (Langfuse, Helicone): per-request cost, but requires proxying — coding agents talk directly to providers.
- **FinOps platforms** (CloudZero, Finout): provider-bill ingestion, org-level only.
- **Engineering-intelligence platforms** (Jellyfish, LinearB, DX, Waydev): AI *adoption/seat* metrics, not cost-per-unit-of-work.

"Cost per unit of shipped work" sits in the seam between all four. The PR
comment is the distribution channel (Codecov playbook): every reviewer sees it.

Approach B (per-dev collector pushes usage records to an orphan
`refs/tokencost` ref; a GitHub Action joins centrally and maintains the
comment) is the planned team-grade successor. v0's `--json` output is the
seam where B will plug in.

## 3. v0 definition

A single npm package. A dev on a feature branch runs `npx prtokens`; the tool
reads their local Claude Code transcripts, attributes token usage to the
commits in the branch's open PR, and upserts a PR comment:

> 🪙 **This PR cost ~$4.83 in tokens** · 2.1M in / 184k out · 3 sessions · claude-sonnet-4-6 + claude-opus-4-8 · 91% attributed
>
> `<details>` per-commit table: sha · message · tokens · cost · sessions `</details>`
>
> *estimated at API rates · generated by prtokens*

Success for v0 is validation signal, not revenue (see §11).

## 4. Architecture

TypeScript, Node 20+, no native dependencies, published to npm (`npx prtokens`
zero-install, matching ccusage-audience habits). One package, six modules with
hard boundaries. The attribution engine is pure functions — no disk, no
network — so it is exhaustively unit-testable.

| Module | Responsibility |
|---|---|
| `transcript-reader` | Locate Claude Code project dirs for this repo (incl. git worktrees) under `~/.claude/projects/`; stream JSONL; emit normalized usage events `{timestamp, model, inputTokens, outputTokens, cacheWriteTokens, cacheReadTokens, sessionId, gitBranch}`. Includes subagent sidechain usage. Dedupes retried messages by message-id + request-id. Skips malformed lines (tallied, reported in `--verbose`). |
| `git-resolver` | Find the open PR for the current branch via `gh`; collect PR commits with authored timestamps from local git; compute patch-ids. |
| `attribution-engine` | Pure join: usage events × commit timeline → per-commit and per-PR totals + coverage stats. All edge-case logic lives here and nowhere else. |
| `pricing` | Tokens × model rates from a bundled LiteLLM pricing snapshot (optional online refresh). Cache reads/writes priced at true rates. Output labeled "estimated at API rates." |
| `comment-renderer` | Markdown for the PR comment: summary line, `<details>` per-commit table, hidden upsert marker (`<!-- prtokens:v1 -->`), per-author section markers. |
| `github-poster` | Upsert via `gh api` using the dev's existing `gh` auth. The tool never stores or handles credentials. |

**Data flow:** reader → resolver → engine → pricing → renderer → poster.
One direction. No state between runs; every run recomputes from source.

**Privacy stance (load-bearing):** transcripts never leave the machine. The
comment contains aggregate numbers only — token counts, dollar estimate,
session count, model names. No prompts, no file paths, no code.

## 5. Attribution semantics

1. A usage event at time *t* on branch *B* attributes to the **first PR commit
   authored at or after *t*** on that branch (work precedes its commit).
   `gitBranch` is per transcript entry, so a session that switches branches
   splits correctly by message, not by session.
2. Usage after the last commit goes to a visible **"uncommitted tail"** bucket;
   if the PR gains commits later, a re-run assigns the tail forward. Usage
   before the first commit rolls into the first commit.
3. Local commits are matched to PR commits by **patch-id, not SHA**, so
   rebase/amend doesn't orphan data. Post-merge squash SHA rewrites are out of
   scope (the comment's job is done by merge time).
4. Entries lacking `gitBranch` (older Claude Code versions) fall back to
   session-time-overlap matching and are reported as **low-confidence**.
5. Every comment states coverage plainly, e.g. *"attributed 91% of observed
   spend, 7% low-confidence."* Never imply false precision.
6. Commits with no attributable agent usage render as $0.00 rows — the
   agent-vs-human contrast is part of the comment's story.
7. Multi-author PRs: each author's run upserts only their own section
   (keyed by GitHub login from `gh`); sections render side by side, and the
   combined total is recomputed from all sections present in the existing
   comment (the comment itself is the only shared state).

## 6. CLI surface

- `npx prtokens` — attribute current branch's open PR; post/update comment.
- `--dry-run` — print the rendered comment instead of posting.
- `--pr <n>` — target a specific PR.
- `--json` — machine-readable output (future Approach-B interface).
- `--verbose` — parse diagnostics (skipped lines, low-confidence detail).

No config file in v0.

## 7. Pricing rules

- Bundled LiteLLM pricing snapshot; works fully offline by default (an
  online refresh of the snapshot is a later enhancement, not a v0 flag).
- Cache reads priced at cache-read rate (~0.1× input), cache writes at
  cache-write rate (~1.25× input). Pricing cache reads as plain input would
  overstate cost ~10× and destroy credibility.
- Dollar figures always labeled "estimated at API rates" — subscription
  (Max/Pro) users' marginal cost is $0 and the number is notional for them.

## 8. Error handling

Rule: **never feel broken, never block the dev.**

| Condition | Behavior |
|---|---|
| No open PR for branch | Friendly hint, exit 0 |
| No transcripts for repo | Say so plainly, exit 0 |
| `gh` missing or unauthenticated | One-line fix instructions, exit 1 |
| Comment post fails | Print rendered markdown to stdout so the run still pays off |
| Malformed transcript lines | Skip, tally, report in `--verbose` only |

## 9. Testing strategy

- **attribution-engine:** exhaustive unit tests on synthetic fixtures —
  multi-session/one-PR, branch-hopping session, uncommitted tail, retry
  dedupe, missing `gitBranch`, rebase patch-id matching, multi-author.
- **transcript-reader:** fixture tests against real anonymized JSONL from
  multiple Claude Code versions (schema drift is the main maintenance risk).
- **comment-renderer:** snapshot tests.
- **e2e:** one manual run against a scratch repo before each release.
- TDD throughout implementation (superpowers discipline).

## 10. Out of scope for v0 (roadmap, not now)

- Other agents (Codex, Gemini CLI, Copilot CLI, Amp — ccusage proves the parsers are feasible).
- Approach B: orphan-ref collector + GitHub Action central join.
- Hosted team dashboard (the paid tier).
- Team aggregation, OTel ingestion, historical backfill tooling, Windows polish.

## 11. Business validation plan

v0 is an experiment with explicit gates before further investment:

1. Ship v0, run it on Samuel's own PRs for 1–2 weeks (dogfood).
2. Publish: npm + GitHub + a screenshot-led post (HN / X, where ccusage's audience lives).
3. **Signal gates:** meaningful traction (stars/installs/issues from strangers,
   teams asking "can my whole team use this?") → build Approach B and the team
   tier. Weak signal → cheap, informative kill.

Known risks accepted: ccusage could add a `--by-pr` flag; GitHub could ship
native Copilot cost-per-PR (strongest platform risk); per-PR cost can be
misread as a performance metric (framing must stay cost-*awareness*, and a
value denominator — e.g. vs. engineer-hours — is a later product question).
